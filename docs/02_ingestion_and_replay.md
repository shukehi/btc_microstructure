# 02 · 采集、订单簿与重放架构

版本：0.1｜状态：实现合同；未完成运行验证

## 1. 组件边界

```text
只读 WS / REST 适配器
        ↓
接收封装与原始日志 ──→ 异常隔离 / 控制事件日志
        ↓
标准化、去重、单位与质量检查
        ↓
成交缓存 / 本地簿 / OI 与资金状态
        ↓
1 秒特征调度器
        ↓
特征快照 + 发布时点
        ↓
描述性状态 → 多期限研究

离线重放器读取同一原始和控制日志，调用同一标准化与计算逻辑。
```

建议采用 asyncio 管理 I/O；单个有序处理器分配 ingest_sequence；写盘使用独立、有界工作队列。网络接收任务不执行大型 DataFrame 运算。技术栈是工程选择，不构成吞吐保证。

## 2. 原始事件与控制事件

每条已收到的消息先进入持久化通道，并保留原始 payload、接收时点、session_id、来源和全局序号。不能因字段解析失败而让原文消失。

控制事件必须包括 `SESSION_OPEN/CLOSE`、`REST_REQUEST/RESPONSE`、`GAP_OPEN/CLOSE`、`BOOK_SYNC_START`、`BOOK_LIVE`、`BOOK_INVALID`、`FEATURE_CUTOFF`、`FEATURE_PUBLISHED` 和 `STORAGE_ERROR`。这些事件帮助重现“当时系统知道什么”，不仅重现最后整理出的行情。

每次 FEATURE_CUTOFF 记录截止时点与输入高水位；处理器可以稍后完成计算，但 FEATURE_PUBLISHED 必须记录实际发布时间。不得用截止时点假装计算已在当时完成。

## 3. 断线、补回和权限

断线后记录受影响来源与缺口起点，使用带随机抖动的指数退避重连。默认退避从 1 秒起，最大 60 秒；这些值是工程默认值。连接轮换后使用新的 session_id，但不能因此重复统计同一成交。

永续官方连接规格包含 24 小时连接寿命与 ping/pong 要求；本项目预设 23 小时主动轮换并保留重叠期成交去重。盘口按单一活动簿处理，新连接建立新 book_epoch，不把两个连接的增量随意交错应用。[S12](08_sources_and_decisions.md#source-s12)

429 进入共享限速退避，418/权限限制进入人工检查状态，不自动更换 IP 继续冲击接口。限流预算由各端点实际规则、响应头与并行任务共同决定。[S08](08_sources_and_decisions.md#source-s08)

可补回的成交进入修订历史；无法补回的盘口序列不伪造。后来的补回数据不改变已经发布的 as_received 特征，只用于单独的修订视图。

## 4. 永续订单簿状态机

### 4.1 状态

| 状态 | 允许行为 | 盘口特征 |
|---|---|---|
| DISCONNECTED | 记录故障、重连 | null |
| SYNCING | 缓存增量、获取快照 | null |
| LIVE | 原子应用有效增量 | 可计算，但仍需覆盖与年龄检查 |
| INVALID | 记录原因、开始新同步 | null |
| STOPPED | 有序停止 | 不生成新值 |

每个有效周期都有独立 book_epoch。不能让 OFI 跨越两个 epoch。

### 4.2 初始化算法

以下衔接规则适用于本项目 Binance USDⓈ-M，不能直接替代现货规则。[S05](08_sources_and_decisions.md#source-s05)

1. 建立 depth 流并缓存完整消息，随后请求 REST 快照。
2. 设快照 lastUpdateId 为 S；丢弃缓存中 u<S 的消息。
3. 找到满足 U≤S≤u 的首条可衔接消息；不存在则继续等待或重新获取更合适的快照。若可用缓存已经明显越过 S，不能强行接上。
4. 从快照创建本地价格档位，按接收顺序原子应用首条及后续消息。
5. 后续有效新消息必须满足 pu=上条已应用消息的 u；否则 INVALID 并重新同步。
6. 数量为绝对值，q>0 替换该档数量，q=0 删除。删除本地不存在的档位是幂等操作，不单独报错。
7. 两侧非空、价格数量有效、bid<ask、覆盖与元数据有效后，记录 BOOK_LIVE 和实际可用时刻。

LIVE 期间完全相同的重复更新忽略；明显过期且 u 不大于已应用 u 的重发可忽略并计数。同一更新标识却不同内容需要隔离并失效，不当作正常重复。

严禁将现货常见的 S+1 衔接习惯直接套进本节。M0 用现场样本再次验证本文规则。

### 4.3 覆盖范围与检查点

保存初始快照两侧最远已知边界。只有在目标 bid 区间下界不低于 known_bid_floor、ask 区间上界不高于 known_ask_ceiling，且期间序列持续有效时，对应深度才视为完整覆盖。

不要为了节省内存每次只留下 Top 10，却继续声称能够精确计算 ±25bps 深度。未知区域的单个新增档位不自动扩张“完整覆盖”的边界。

默认每 60 秒保存有效簿检查点，另在关闭前保存。检查点含完整已知状态、book_epoch、元数据版本、最后应用 u、输入日志游标、已知覆盖边界、有效时点和校验和。

重放从检查点开始，仅应用游标之后且可衔接的记录。发现检查点校验失败时停止使用它，退回更早的可信检查点或重新执行原始同步过程。

## 5. 两种时间视图

### 5.1 默认 `as_received`

这是第一版主要研究视图，时间轴使用真实本地接收时间。对 UTC 秒边界 t，成交窗口为 [t−W,t)，取真实接收时间落入该区间、且在该截止输入高水位内的记录。相同时间按 ingest_sequence 决定稳定顺序。

状态变量使用截至 t 已接收的最新有效观测。订单簿使用截至该截止已经有效的状态；同步完成晚于截止时点则该时点仍不可用。

特征额外记录实际 `feature_available_ns`，且不得早于截止时点和所有使用输入的可用时点。任何研究中的可执行决策都只能从这个发布时刻开始，再叠加所声明的执行延迟。

接收窗口衡量的是本机所见订单流，不宣称它是交易所精确事件窗口。网络突发会影响接收窗口；因此必须保留事件时钟和 lag 指标用于敏感性检查。

### 5.2 可选 `event_time_revised`

用于事后描述市场事件。成交按源 T、有源时间的其他流按明确指定的时间字段对齐，可以纳入补回记录。缺少源时间的现货 BBO 不得凭接收时间悄悄填入同一事件时间轴。

此视图按 source、dataset_revision 和 watermark 策略单独保存。默认不进入“真实当时可交易”的结论。归档数据需要仿真延迟时，另外使用 `event_time_simulated` 名称并保存延迟假设。

### 5.3 禁止混用

不得让特征采用后来补齐的事件时间数据，而入场价格仍取信号原本出现的旧价格。不得用双向插值或 nearest join 让后来 OI 出现在更早时点。不得用现货收到时间与永续事件时间直接推断交易所内领先关系。

## 6. 状态对齐与过期规则

采用向后匹配（backward as-of），同时检查来源是否健康和观测年龄。默认阈值如下，均可配置并要求敏感性报告：

| 数据 | 默认年龄限制 | 额外条件 |
|---|---:|---|
| 最优报价 | 2000ms | 两侧有效、连接状态单独报告 |
| 永续簿 | 最后有效更新 2000ms | LIVE、序列有效、覆盖足够 |
| mark/index | 5000ms | 同一条来源消息中的字段优先 |
| OI 接收轮询 | 15000ms | 源时间若存在还需≤30000ms |
| 跨现货/永续报价 | 各自≤2000ms | 两条所用报价的接收时点差≤1000ms |

强平没有新消息不自动判为故障；该流以连接健康、订阅状态和来源覆盖限制描述。重复 OI 返回的成功轮询与真实观测的新鲜程度分开计算。

墙钟跳变、明显负 lag 或本机时间同步异常需记录 CLOCK_UNCERTAIN。单调时钟用于本进程耗时和稳定排序；不能用单调时钟与另一台机器直接比较。

## 7. 持久化合同

```text
data/
  raw/venue=binance/market=um_perpetual/stream=um_agg_trade/date=YYYY-MM-DD/
  normalized/table=trades/market=um_perpetual/date=YYYY-MM-DD/
  checkpoints/market=um_perpetual/symbol=BTCUSDT/
  features/view=as_received/version=0.1/date=YYYY-MM-DD/
  labels/run_id=.../horizon_s=.../
  reports/run_id=.../
  manifests/
```

raw 日期取实际接收 UTC 日期；归档原文件按数据覆盖日期和 archive 标识保存。跨日窗口读取前一日所需分区，不在午夜丢弃滚动状态。

原始日志使用可轮换、可恢复的逐记录文件；关闭后可以压缩。标准化和特征使用 Parquet，默认 ZSTD；不要逐条消息创建一个文件。文件先写临时名，完成并校验后再原子提交，并登记到 manifest。

默认 raw 持久化批次最长 1 秒；这是目标而非零丢失保证。异常断电可能丢失最后未提交部分，重启必须从最后可信提交处登记 UNCERTAIN_GAP，不声称 exactly-once 接收。

每个提交清单记录：路径、SHA256、行数、时间范围、来源、schema_version、质量计数和前后输入游标。不能在文件尚未成功提交时把消费游标永久前移。

## 8. 积压与故障处理

有界队列必须同时监控记录数量、估计字节数和最老记录年龄。积压达到预警时先告警与降低非必需 REST 任务；达到容量时不得覆盖旧记录。必要时主动断开受影响流，登记缺口并重新同步。

磁盘空间低于配置警戒线时禁止启动新的大型回填；无法继续可靠写盘时，停止宣称数据连续，并结束受影响特征发布。不得自动删除唯一原始日志以掩盖容量不足。

## 9. 重放的一致性要求

确定性重放读取原始事件和原始调度／可用性控制日志，不能凭本次处理速度重新发明历史发布时间。相同输入、配置和版本必须得到相同记录选择、去重、book_epoch、质量标志和特征值。

Decimal、定点、ID 与状态要求完全一致；Float64 在测试规范约定的误差内一致。Parquet 二进制字节不要求相同，规范化后的逻辑行与排序必须一致。

事件时间重建与接收时间重放是不同任务，不把两者结果不一致直接判为算法错误。更快或更慢系统的假想结果必须单独标为模拟运行。
